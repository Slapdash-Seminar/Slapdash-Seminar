# 요구사항

이 앱이 무엇을 해야 하는지 적는 곳이다. 두 폴더로 나눈다.

| 폴더 | 담는 것 | 누가 고치나 |
|---|---|---|
| `정적/` | 과제의 틀. 목표, 필수 기능, 기한, 플랫폼과 기술 스택, 서버·보안 제약 | 사람만. 에이전트는 읽기만 한다 |
| `가변/` | 기능 세부, 우선순위, 성능·보안·이식성 수치, 검증 기준, 용어, 화면 설계 | 누구나. 여건에 따라 언제든 PR 로 고친다 |

옛 요구사항서(운영 폴더의 `[1차] 요구사항서_v3.0.1.docx`, 2026-10-09)는 한 파일에 모든 것을 고정해 두었다. 화면과 결정이 바뀔 때마다 문서 전체를 다시 만들어야 했다. 그래서 바뀌지 않는 틀만 `정적/` 에 묶어 두고 나머지는 `가변/` 에서 조금씩 고친다.

## 읽는 순서

1. `정적/과제 틀.md` 를 먼저 읽는다. 여기 적힌 것은 전제다.
2. 맡은 모듈의 `가변/기능/<모듈>.md` 를 읽는다. 모듈 이름은 브랜치 머리와 같다(`.claude/rules/repo-rules/모듈과 브랜치.md`).
3. 고칠 일이 생기면 `가변/README.md` 의 협업 규칙을 따른다.

## 정적과 가변이 부딪히면

정적이 이긴다. 가변 요구사항이 정적과 맞지 않으면 가변을 고친다. 정적을 바꿔야 한다고 보이면 고치지 말고 이슈를 연다(`정적/README.md`).

## 요구사항 ID

| 종류 | 꼴 | 예 | 있는 곳 |
|---|---|---|---|
| 정적 | `ST-번호` | `ST-03` | `정적/과제 틀.md` |
| 기능 | `FR-<모듈 약어>-번호` | `FR-SCH-04` | `가변/기능/<모듈>.md` |
| 성능·보안·이식성·신뢰성 | `PR-` `SR-` `PO-` `RR-` 번호 | `SR-02` | `가변/비기능.md` |
| 검증·인수 | `VR-<모듈 약어>-번호`, `AT-번호` | `VR-NOT-01` | `가변/검증.md` |

- 모듈 약어는 `SKL` 골격, `MEM` 회원, `TEAM` 팀, `SCH` 일정, `NOT` 공지, `FILE` 파일, `ADM` 관리자, `ALR` 알림, `INF` 인프라다.
- 기능과 검증 ID 에 모듈 약어를 넣는 까닭은 여러 사람이 동시에 새 번호를 따도 겹치지 않게 하려는 것이다.
- 한 번 쓴 ID 는 다시 쓰지 않는다. 없앤 요구사항은 지우지 않고 상태를 `폐기` 로 바꾼다.
- 코드, 커밋, PR 에서 요구사항을 가리킬 때는 이 ID 를 쓴다.
