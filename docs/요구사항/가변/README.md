# 가변 요구사항

기능 세부와 수치처럼 개발하면서 바뀌는 요구사항이다. 사람도 에이전트도 고칠 수 있다. 여럿이 동시에 고쳐도 엉키지 않게 아래 규칙을 지킨다.

## 파일

| 파일 | 담는 것 | 맡는 사람 |
|---|---|---|
| `기능/<모듈>.md` | 그 모듈의 기능 요구사항(FR) | 모듈 담당 |
| `비기능.md` | 성능(PR), 보안(SR), 이식성(PO), 신뢰성(RR) | 골격 담당 |
| `검증.md` | 검증 기준(VR)과 인수 시험(AT) | 시험 담당. VR 행은 그 모듈 담당도 고친다 |
| `용어.md` | 용어와 자료 사전 | 누구나 |
| `화면.md` | 화면 설계(Figma) 링크, 섹션, 화면 이름, 바꾸는 법 | 화면 설계 담당 |

모듈과 담당은 `.claude/rules/repo-rules/모듈과 브랜치.md` 에 있다. 기능을 모듈 파일로 나눈 까닭은 담당이 자기 파일만 고치게 해서 같은 줄을 두 사람이 동시에 고치는 일을 줄이려는 것이다.

## 한 줄의 꼴

기능 요구사항 한 줄은 이렇게 쓴다.

| ID | 요구사항 | 우선순위 | 상태 | 검증 | 근거 |
|---|---|---|---|---|---|
| FR-SCH-04 | 참여자가 달력에 가능 시간을 넣을 수 있어야 한다 | 필수 | 합의 | VR-SCH-02 | 옛 FR-08, D2 |

- 요구사항은 "~할 수 있어야 한다" 로 끝나는 한 문장이다. 화면 배치나 구현 방법은 쓰지 않는다.
- 우선순위는 `필수`, `2차`, `미정` 중 하나다.
- 검증 칸에는 이 요구사항을 확인하는 VR ID 를 쓴다. 아직 없으면 `없음`.
- 근거 칸에는 이 줄이 생기거나 바뀐 까닭을 가리킨다. 모듈 결정 번호(`D번호`), PR 번호(`#번호`), 옛 요구사항서 ID(`옛 FR-08`) 중 있는 것을 쓴다.

## 상태

| 상태 | 뜻 | 누가 바꾸나 |
|---|---|---|
| 제안 | 누군가 필요하다고 적었다. 아직 만들지 않는다 | 누구나 |
| 합의 | 모듈 담당이 받아들였다. 만들어도 된다 | 모듈 담당 |
| 구현 | 코드가 main 에 들어갔다 | 그 코드 PR |
| 검증 | 검증 칸의 VR 을 통과했다 | 시험한 사람 |
| 보류 | 지금은 하지 않는다. 까닭을 근거 칸에 쓴다 | 모듈 담당 |
| 폐기 | 하지 않기로 했다. 줄을 지우지 않는다 | 모듈 담당 |

## 고치는 법

1. 요구사항만 바꾸면 그 모듈 브랜치로 PR 을 연다. 범위는 `문서`, 모듈은 그 파일의 모듈이다.
2. 코드를 짜다가 요구사항이 바뀌면 같은 코드 PR 에서 고친다. 구현이 끝난 줄은 상태를 `구현` 으로 바꾼다.
3. 다른 모듈의 파일을 고쳐야 하면 PR 에서 그 담당을 멘션하고 동의를 받은 뒤 병합한다.
4. 회의나 화면 검토에서 바뀌었으면 그 모듈 `.claude/memory/<모듈>/결정.md` 에 결정을 남기고 근거 칸에 번호를 쓴다.
5. 새 ID 는 그 파일의 마지막 번호 다음을 쓴다. 두 PR 이 같은 번호를 따면 나중에 병합하는 쪽이 번호를 올린다.

## 에이전트가 고칠 때

- 근거 없이 고치지 않는다. 사람의 지시, 결정 번호, PR 중 하나가 있어야 한다.
- 우선순위를 바꾸거나, `폐기`·`보류` 로 바꾸거나, 다른 모듈 파일을 고칠 때는 사람이 시킨 경우에만 한다.
- 고친 줄은 PR 본문 `변경 내용` 에 ID 로 적는다.
- 고치다가 `정적/` 과 부딪히면 멈추고 사람에게 묻는다.

## 옛 요구사항서에서 옮기기

각 `기능/<모듈>.md` 머리에 옛 요구사항서 v3.0.1 에서 옮겨 올 ID 를 적어 두었다. 옮길 때는 그 모듈 담당이 지금 화면과 결정에 맞춰 문장을 다시 쓰고, 근거 칸에 옛 ID 를 남긴다. 그 뒤 화면 데모에서 바뀐 것이 많으므로 옛 문장을 그대로 붙여 넣지 않는다.
